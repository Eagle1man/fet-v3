# Принятые решения

Документ фиксирует то, что нельзя выяснить из кода: почему сделано именно так.

## 1. Год в датах — 2026, не сдвигается

В выгрузке `Rasp_*.27` все даты относятся к 2026 году. Сдвиг на год меняет
день недели (2026 и 2027 не совпадают по календарю), поэтому автоматический
перенос невозможен. Решение: файлы строятся по фактическим датам, а
расхождение с названием периода зафиксировано в `docs/00_audit.md` (п. 3.1).
Ответственность за правильную выгрузку — на владельце данных AVTOR.

## 2. Перекрытие периодов: побеждает более поздняя выгрузка

`Rasp_2.02` и `Rasp_2.03` содержат дни 24–28.02. Сравнение показало: в
`2.03` те же занятия, но с исправлениями (например, «Родная литература»
переехала из 604б в 315, у ЮД201 заменён предмет). Если оставлять обе версии,
на стыке возникают ложные конфликты. Решение: для даты, встречающейся в
нескольких периодах, берутся строки из более позднего периода. Заменённые
строки считаются в статистике, расхождения по аудитории попадают в отчёт
как «версии занятия».

## 3. Конфликты не удаляются

Требование ТЗ и правил проекта. Реализация: активность остаётся в `.fet`,
получает `Weight_Percentage=50` вместо 100, а слот и обе строки источника
пишутся в `out/conflicts/<имя>.md`. FET вправе перенести такую пару — это и
есть правильное поведение «проект, а не приказ».

## 4. `Преп_*.xls` — это нагрузка, а не запреты

ТЗ называет эти файлы «ограничениями занятости». Фактически внутри — список
занятий преподавателя за период (вид, дисциплина, дата, день, время,
аудитория, группа). Из него нельзя вывести `ConstraintTeacherNotAvailable`:
отсутствие строки означает «нет пары», а не «не может работать».

Решение: справочники используются для сверки и описаны в аудите; запреты
задаются вручную — `FETV3_CONSTRAINTS` (JSON). Формат проверен на реальном
`fet-cl`: файл с `ConstraintTeacherNotAvailableTimes` и
`ConstraintRoomNotAvailableTimes` открывается и генерируется без ошибок.

## 5. Вместимость аудиторий — заглушка 999

В источниках нет ни вместимости, ни корпуса. FET отказывается строить
расписание, если вместимость меньше числа студентов (ошибка «no allowed
preferred room»). Поэтому в `.fet` стоит 999 — явно помеченная техническая
заглушка «не ограничивать», а не выдуманное значение. Число студентов в
группах настоящее (из `StudInLesson`).

## 6. Подгруппа не занимает родительскую группу

При проверке конфликтов активность подгруппы блокирует только свою подгруппу;
активность всей группы блокирует группу и все её подгруппы. Иначе две
параллельные ветки (`Subg=1` и `Subg=2` в одном слоте) считались бы
конфликтом, хотя это норма.

## 7. Схема FET — только 7.10.5 и только проверенная бинарником

`ElementTree.parse` принимает файл, который FET отвергает. Первая версия
генератора использовала устаревшие одиночные теги
(`ConstraintActivityPreferredStartingTime`, `<Day>`, `<Hour>`) — FET 7.10.5
на них отвечал `Cannot read input file`. Рабочая схема — множественные:
`ConstraintActivityPreferredStartingTimes` с `Preferred_Starting_Time`,
`Preferred_Starting_Day`, `Preferred_Starting_Hour` (имя пары, не номер), и
`ConstraintActivityPreferredRooms` с `Preferred_Room`.

## 8. Ручные правки живут в БД, а не в `.fet`

Панель меняет строку `lessons` и пишет `change_log` в одной транзакции.
Откат возвращает предыдущие значения по строке источника. ETL при повторном
прогоне удаляет и заново вставляет строки периода, поэтому после загрузки
выполняется `journal.replay`: активные (не отменённые) правки применяются
к новым строкам. Иначе `run.py all` молча стирал бы работу сотрудника.

## 9. Проверка выполняется реальным `fet-cl`

`run.py validate` запускает `fet-cl.exe` с лимитом времени из `.env`.
«Time exceeded» не считается ошибкой файла, но фиксируется в отчёте.
Фатальность определяется по сообщениям FET (`Cannot read`, `Cannot precompute`,
`data is wrong`, `aborting`). На текущей выгрузке все 7 файлов проходят
полную генерацию без нарушенных мягких ограничений.

## 10. ИИ отвечает только через инструменты

Ассистент (`ai/agent.py`) не получает расписание в промпт и не пишет `.fet`.
Он вызывает функции из `ai/tools.py`, результат берётся из БД и отчётов.
Если модель отвечает, не вызвав инструмент, ассистент один раз требует
вызвать его — это защита от «уверенной выдумки».

Проверка на живой модели показала: `qwen2.5:1.5b` инструменты игнорирует
(ответ «в данных нет» при наличии двух пар), `qwen2.5:7b-instruct` вызывает
`query_lessons` с корректными аргументами. Поэтому модель по умолчанию — 7b.

Правка всегда идёт в два шага: `edit_lesson` без `confirm` возвращает diff,
применение — только после согласия человека (`run.py chat`). Для поиска
занятия используется `selector` (группа, дата, предмет, пара), а не номер
строки: модель не должна угадывать `source_row`.

## 11. Один конвейер для CLI, UI, ИИ и веба

Логика сборки и проверки вынесена в `pipeline.py`. CLI печатает, панели
показывают, ассистент вызывает — все используют один код. Иначе проверки
в интерфейсах расходились бы с тем, что делает `run.py`.

## 12. Публикация повторяет контракт сайта, а не придумывает свой

Действующий сайт отдаёт расписание через
`read-file-groups.php` (`do=groups`, `do=schedule&group=…`). Экспорт
формирует ровно эти структуры (`groups.json`, `data.json`) с теми же
полями занятия, поэтому его можно отдать администратору сайта без
переписывания PHP. Дополнительно собирается автономный просмотрщик:
ВМ вуза может показать расписание без доступа к Bitrix.

Сопоставление «группа → академия» — снимок `do=groups` в
`config/site_groups.json`. Если группа не найдена, она попадает в
`FETV3_SITE_FACULTY`; выдумывать принадлежность нельзя.

## 13. Веб-панель: один процесс, один пароль, CSRF

FastAPI + Jinja2 без сборки фронтенда: на ВМ достаточно Python.
Правка и публикация требуют входа; чтение можно открыть флагом
`FETV3_PUBLIC_READ`. Пароль один на всех — осознанное ограничение MVP,
роли и LDAP вынесены в следующий этап.

Долгие операции (сборка, `fet-cl`, экспорт) идут в фоне: HTTP-запрос не
держит таймаут, а страница показывает статус задания. Второе задание
одновременно не запускается — иначе два процесса писали бы одни файлы.

Проверка `fet-cl` на Linux-ВМ требует Linux-сборки FET; в контейнере
по умолчанию доступны просмотр, правка и публикация.
